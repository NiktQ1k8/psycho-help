# Правила работы

- Меняй только фронтенд. Код бэкенда менять запрещено; бэкенд можно читать, проверять и запускать локально.
- С локальной базой данных можно выполнять любые операции без дополнительного согласования: удалять данные, очищать или пересоздавать базу, применять миграции.
- Делай правильно, но максимально просто. Не добавляй абстракции и зависимости без необходимости.
- Не делай коммит без просьбы. Если попросили: автор — Codex, человек — соавтор; подпиши коммит и проверь подпись. Название — по Conventional Commits, на простом английском. Не пушь без просьбы.
- При подписи пользовательским ключом указывай коммиттером владельца ключа с его именем и подтверждённым на GitHub email. Авторство Codex и соавторство пользователя задавай отдельно; коммиттером Codex в этом случае не указывай.
- Проверяй подпись через `git verify-commit`. Для SSH используй доверенный публичный ключ и email его владельца в `gpg.ssh.allowedSignersFile`. После переписывания истории заново проверяй подписи всех пересозданных коммитов.
- Локальная проверка подписи не подтверждает статус Verified на GitHub. Для опубликованных коммитов проверяй `verification.verified` и `verification.reason` через GitHub API. Для неопубликованных явно сообщай, что проверена только локальная подпись; ради проверки ничего не пушь без просьбы.
- Сайт для русскоязычных пользователей: тексты, ошибки и подписи доступности пиши по-русски.
- Тщательно обрабатывай все ошибки. Сообщения должны понятно объяснять пользователю, что произошло и что можно сделать дальше; не показывай технические подробности и заглушки.
- Всё время на сайте — московское, независимо от часового пояса пользователя. Используй `src/shared/lib/date-time.ts`.
- Не используй `FC` / `React.FC`. Объявляй компоненты обычными функциями с типизированными пропсами.
- Используй именованные экспорты при объявлении: `export const Component = ...`. Не добавляй `export default` в конце файла.
- Названия собственных интерфейсов начинай с `I`, типов — с `T`.
- Компоненты и их папки называй в PascalCase, как в новостях: `pages/News/ui/NewsList/NewsList.tsx`. Стили рядом — `NewsList.module.scss`, внутренние компоненты — `components/NewsCard/`, ресурсы — `assets/`.
- Служебные папки называй по назначению: `ui`, `api`, `model`, `assets`. Не создавай файлы-бочки и `index.ts(x)`; используй прямые импорты. Не переименовывай несвязанные с задачей файлы.
- Для размеров используй `px`, а не `rem`.
- Не используй `:global` для стилей библиотек. Создавай отдельный обычный SCSS рядом с компонентом и импортируй его. Ограничивай правила атрибутом обёртки: как `Gallery.swiper.scss`, где `.swiper-*` вложены в `[data-image-gallery]`, а атрибут установлен в `Gallery.tsx`.
- CSS Modules изолируют имена классов, но не теги и атрибуты. Даже внутри `[data-theme='dark']` привязывай правила к локальному классу компонента.
- Проверяй светлую и тёмную темы, а также мобильную вёрстку.
- Временные тесты для проверки задачи после проверки удаляй. Постоянные тесты оставляй только для авторизации, cookie и работы с локальным бэкендом.
- Не пиши лишние комментарии: поясняй только неочевидные причины решений.
